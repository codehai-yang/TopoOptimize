## 用户需求

排查并修复 `PowerDistributionDriveOptimization.java` 中配电/驱动优化枚举算法的逻辑缺陷：用户在测试数据中将某个用电器的 `changeType` 改为 2（位置可变），期望该用电器的位置被枚举进方案，并且"总方案数"与"枚举出的方案数 / 有效方案数"保持一致；但实际有效方案数始终为 0，与"仅改回路可连接电器件（连接关系变化）时正常"的表现不一致。

## 核心问题

- 计数函数 `calculateOptimizationCombinations` 与真实枚举口径不一致：它把每个位置可变用电器的 `positions.size()` 无条件乘进全局乘积，未与"连接关系赋值"耦合，导致总方案数被 `allPoint` 全量放大。
- 放大后的总方案数一旦超过阈值 `caseNumbe(10000)`，第 308 行 `if (combinations <= caseNumbe)` 为 false，整段枚举被跳过、退化为遗传算法分支，用户看到"有效方案数=0"且对不上。
- 仅改连接关系时数值小、能正常进入枚举，因此"看起来没问题"。
- 另一处口径差异：`allPossibleApps` 会把"仅作为连接选项（loopElecById 值）出现、但并非某回路真实起点/终点"的用电器也算进位置乘积，而枚举侧 `appPositionDomains` 只收集真正落在 `affectedLoopIds` 起点/终点的用电器。

## 修复目标

使"总方案数  ==实际枚举出的方案总数"，既不虚高导致误跳过枚举，也不漏算；同时保证 `changeType==2 `时若 `allPoint` 为空能给出明确日志而非静默 0 方案。

## 技术栈与现状

- 现有项目：Java 17 + Maven，单文件大方法结构（`PowerDistributionDriveOptimization.java`，约 2533 行），枚举采用"连接关系变量域回溯 + 位置组合乘积"两段式。
- 不涉及新框架、新依赖；遵循既有包结构与编码规范（4 空格缩进、小驼峰）。

## 实现思路

核心策略：让 `calculateOptimizationCombinations` 与枚举走完全一致的逻辑——复用同一套 `varDomains`（连接关系变量域，含 `changeType==2` 对应的位置桩变量 `E_L_/S_L_`）、同一个 `togetherGroup`/`mutualGroup` 约束做连接关系回溯；在每一个"完整连接赋值"叶子节点上，按照 `generateSchemesForAssignment` 的口径解析 `loopToStartApp/loopToEndApp`、收集真正被选中（起点/终点）且 `elecChangeablePosition` 非空的用电器，把它们的位置数相乘，再在所有连接赋值间求和。

数学上，枚举对每个连接赋值产生 `Π(positions.size())` 个方案，计数对同一个连接赋值累加同样的乘积，因此"总方案数 == 枚举方案总数"必然成立，彻底消除虚高与对不上的问题。

### 关键技术决策

1. **抽取共享的变量域构建方法**：将 `enumerateAllSchemes`（L1888-1994）里构建 `varDomains`（含位置桩变量）、`coveredLoopIds`、`togetherGroup` 交集、`mutualIdToVarKeys`、`varsInAnyMutualGroup`、`varKeys` 的逻辑抽取为独立方法（如 `buildConnectionVarDomains(...)`），由枚举与计数复用。这样两处永不失同步，符合 DRY/KISS，且对枚举行为零改动（仅重构提取，不改语义）。
2. **计数改为"连接回溯 + 叶子乘积"**：`calculateOptimizationCombinations` 内部复用上述 `varDomains` + 互斥剪枝（`usedEndApps`）做回溯，叶子处调用一个新的 `countSchemesForAssignment(assignment, ...)`，其收集位置可变用电器的规则与 `generateSchemesForAssignment` Step1/Step2 完全一致（含 `affectedLoopIds` 的 together/mutual 展开、`E_G_/S_G_/E_L_/S_L_` 解析、`appPositionDomains` 收集）。叶子返回值为 `Π(positions.size())`，空集返回 1（对应枚举里 `appPositionDomains.isEmpty()` 时生成 1 个方案）。
3. **保留 `caseNumbe` 阈值与剪枝**：回溯仍遵守 L2025 的同名阈值提前退出与互斥剪枝，避免计数侧额外开销；计数只做整数乘法、不构造方案对象，性能与枚举回溯同量级，无新瓶颈。
4. **`changeType==2` 空位置保护**：在 L224-225 写入 `elecChangeablePosition` 后，若 `allPoint` 为空则打印明确警告日志，避免静默产出 0 方案。

### 实现注意（防止回归）

- 重构提取 `buildConnectionVarDomains` 时必须与现有 `enumerateAllSchemes` 逐行等价，先保证 `mvn clean compile` 与老样本枚举数不变。
- 互斥剪枝（`usedEndApps` / `varsInAnyMutualGroup`）在计数回溯中必须与枚举一致，否则计数与枚举会在互斥组场景下再次对不上。
- 不改动 `buildSchemeFromAssignment`、`enumeratePositionsForAssignment` 等枚举执行逻辑，只对齐"口径"，控制影响面。
- 日志沿用现有 `System.out.println` 风格与 UTF-8，避免打印大对象。

## 架构设计

- 不引入新架构/新模式，仅在现有单文件内做"抽取共享方法 + 重写计数函数"，保持原两段式枚举结构不变。
- 数据流：输入(loopInfos/appPositions) → 构建 elecChangeablePosition（L185-228，微调空保护）→ 构建连接变量域（共享方法）→ 计数回溯(叶子乘积求和) 与 枚举回溯(叶子位置组合) 共用同一变量域与约束。
